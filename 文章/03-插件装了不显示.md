# 插件装了却不显示：一次静默禁用的排查

## 现象

一个编辑器/客户端的插件系统。你按文档装了插件：

- `package.json` 的 `dependencies` 里有它 ✅
- 配置里的 `bundles` 列表里有它 ✅
- 启动日志没有 `error`，没有 `warn` ✅
- 重启了三次 ✅

**界面上就是没有那个按钮。**

---

## 排查顺序

先别怀疑插件本身。按这个顺序查，从便宜的到贵的：

### 1. 插件真的被加载了吗

看启动日志里的 entries 列表（有的叫 `boot graph`、`modules`、`loaded`）。如果列表里没有你的包，说明它连加载阶段都没进，问题在**校验**，不在插件代码。

### 2. 校验卡在哪一层

这类系统通常有三层校验：

| 层 | 检查什么 | 失败表现 |
|---|---|---|
| 版本门槛 | 宿主版本 vs 插件声明的兼容范围 | 静默禁用 |
| 依赖解析 | 插件自己的依赖能不能装上 | 安装失败或半截 |
| 运行时 | 插件 `apply()` 有没有抛错 | 日志有 stack |

你这种情况通常是**第一层**。

### 3. 打开调试日志

```bash
DEBUG=* node bin.js start 2>&1 | grep -i "skip\|disable\|incompatible\|peer"
```

很多宿主在静默禁用时会打一行 `debug` 级别的日志——默认看不到。

---

## 根因：peer 版本上限

插件在 `package.json` 里声明：

```json
{
  "peerDependencies": {
    "@scope/host": ">=0.2.0-rc.0 <0.2.1-rc.3"
  }
}
```

你跑的是 `0.2.1-rc.3`。

**上限是开区间，`rc.3` 不满足 `<0.2.1-rc.3`。**

于是宿主判定「不兼容」，把整个包从 boot 图里摘掉。不报错的原因很实际：插件系统的设计假设是「不兼容就不加载」，报错反而会刷屏。

---

## 为什么这种坑特别难查

因为**错误发生在你完全看不到的地方**。

- 安装成功了（依赖装上了）
- 文件都在（没被删）
- 配置对了（写进去了）
- 启动正常（宿主起来了）

四个 ✅ 同时成立，功能是坏的。

这周我在另一个场景遇到同一个模式：一个 AI 工具的插件系统里，两个子包 `studio-panel@0.1.0` 和 `dsh-dog@1.2.0` 的 peer 上限都写着 `0.2.1-rc.2`，运行时是 `rc.3`。宿主把它们**逐个**校验、逐个摘掉，界面上就是少了两个按钮。

---

## 怎么修

### 方案 A：改兼容性豁免（推荐）

大部分宿主都留了后门，名字不一样：

- `compatibility.json`
- `overrides`
- `peerExemptions`
- `allowedVersions`

格式类似：

```json
{
  "exemptions": [
    { "name": "@dsh-novel/studio-panel", "reason": "peer cap too low" },
    { "name": "@dsh-external/dsh-dog", "reason": "peer cap too low" }
  ]
}
```

**这里有个大坑**：文件必须是**无 BOM 的 UTF-8**。

PowerShell 5.1 的 `Set-Content -Encoding UTF8` 会写 BOM（`EF BB BF`），宿主解析 JSON 时直接失败，整个文件失效——表现是「我明明加了豁免，还是没生效」。

用这个写：

```powershell
[System.IO.File]::WriteAllText(
  $path,
  $json,
  (New-Object System.Text.UTF8Encoding($false))   # $false = 不写 BOM
)
```

### 方案 B：改插件自己的 peer 范围

如果插件是你自己维护的，直接把上限放开：

```json
"peerDependencies": { "@scope/host": ">=0.2.0-rc.0" }
```

### 方案 C：降宿主版本

最笨但最稳。如果你不依赖新版本特性，退回 `rc.2` 就行。

---

## 怎么验证修好了

**不要看界面。** 界面可能因为缓存、主题、布局原因不显示。

看 boot 图：

```bash
# 用 profile 的副本起独立实例，不要动主环境
node bin.js start 2>&1 | grep -o '@[a-z-]*/[a-z-]*' | sort -u
```

80 条 entries 里应该出现你那个包的名字。出现了，才算真的加载了。

---

## 换个角度

这类问题的通用诊断句是：

> **「装了」和「加载了」是两件事，「加载了」和「显示了」又是两件事。**

三层各有各的失败方式：

1. 装了 → 看 `node_modules` 里有没有 `package.json`
2. 加载了 → 看 boot 图里有没有名字
3. 显示了 → 看 UI 渲染（可能被权限、开关、布局藏起来）

每层都验证一遍，能省掉很多「重启试试」。
